# ENSIP-28: Batch Registration and Renewal

## Abstract

This ENSIP defines a standardized interface for batch registration and renewal of ENS names, allowing multiple names to be registered or renewed in a single transaction.

## Motivation

Users and organisations that manage multiple ENS names currently must submit separate transactions for each registration or renewal. This is inefficient in terms of both gas costs and user experience. A batch interface would reduce total gas consumption through amortised fixed costs (base transaction fee, storage slot warm-up) and simplify portfolio management for large name holders.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Batch Registration

```solidity
struct RegistrationRequest {
    string name;
    address owner;
    uint256 duration;
    bytes32 secret;
    address resolver;
    bytes[] data;
    bool reverseRecord;
}

function batchRegister(RegistrationRequest[] calldata requests) external payable;
```

The `batchRegister` function MUST process each request in order, applying the same validation rules as the existing single-name `register` function. If any individual registration fails, the entire batch MUST revert.

### Batch Renewal

```solidity
function batchRenew(string[] calldata names, uint256 duration) external payable;
```

The `batchRenew` function MUST renew all specified names for the given duration. The total cost MUST equal the sum of individual renewal costs. If any name cannot be renewed (e.g., it is not currently registered), the entire batch MUST revert.

### Batch Commit

Since the existing registration process requires a commit-reveal scheme, a corresponding batch commit function is required:

```solidity
function batchCommit(bytes32[] calldata commitments) external;
```

### Refund Handling

If the total ETH sent exceeds the total cost of all operations, the contract MUST refund the excess to `msg.sender`.

## Rationale

An all-or-nothing approach (reverting the entire batch on any failure) was chosen over partial execution to simplify error handling and prevent situations where users pay for a transaction that only partially succeeds. Users who want partial execution can split their requests into separate batches.

## Backwards Compatibility

This ENSIP introduces new functions and does not modify existing registration or renewal interfaces. The single-name functions remain available and unchanged.

## Security Considerations

Batch operations increase the maximum gas consumption per transaction. Implementations SHOULD enforce a reasonable upper bound on batch size to prevent transactions that exceed block gas limits. A maximum of 50 names per batch is RECOMMENDED.

The refund mechanism MUST use a pull pattern or `call` with proper reentrancy guards to prevent reentrancy attacks during excess ETH refunds.
