# ENSIP-30: Name Expiry Notifications

## Abstract

This ENSIP defines an on-chain notification system that allows ENS name owners to register notification hooks — smart contracts that are automatically called when a name approaches its expiry date. This enables automated renewal workflows, alerting services, and programmable responses to impending name expirations.

## Motivation

ENS name expiry is a silent event. Name owners receive no on-chain signal when their names are about to expire, relying entirely on off-chain services (email alerts, app notifications) to remind them to renew. This creates several problems:

1. Off-chain notification services are centralised points of failure.
2. Smart contracts that depend on ENS names cannot programmatically react to impending expirations.
3. DAOs and multisigs have no automated mechanism to trigger renewal governance proposals.

An on-chain notification system would allow name owners to set up self-sovereign, programmable alerts that are as decentralised and reliable as the names themselves.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Notification Registry

A singleton `NotificationRegistry` contract SHALL be deployed, allowing name owners to register callback contracts:

```solidity
interface INotificationRegistry {
    function registerHook(bytes32 node, address hook, uint256 leadTime) external;
    function removeHook(bytes32 node, address hook) external;
    function getHooks(bytes32 node) external view returns (HookInfo[] memory);
}

struct HookInfo {
    address hook;
    uint256 leadTime;
}
```

Where `leadTime` is the number of seconds before expiry at which the hook should be triggered.

### Notification Hook Interface

Contracts registered as hooks MUST implement:

```solidity
interface IExpiryHook {
    function onExpiryNotification(bytes32 node, uint256 expiryTimestamp) external;
}
```

### Trigger Mechanism

Notifications are triggered by a permissionless `notify` function on the registry:

```solidity
function notify(bytes32 node) external;
```

Anyone MAY call `notify` for any node. The registry MUST check whether the name's expiry minus `leadTime` has been reached and, if so, call the hook. Each hook MUST only be called once per expiry cycle.

### Incentive Layer

To incentivise timely notification, callers of `notify` MAY receive a small bounty funded by the name owner. The bounty amount is set during hook registration:

```solidity
function registerHook(bytes32 node, address hook, uint256 leadTime, uint256 bounty) external payable;
```

## Rationale

A pull-based notification model (where anyone can trigger `notify`) was chosen over a push-based model (where the registrar automatically calls hooks on expiry) because push-based models add gas costs to every registration and renewal transaction, even for names that have no hooks registered. The pull model externalises the cost to those who benefit from the notification.

## Backwards Compatibility

This ENSIP introduces a new standalone contract and does not modify the ENS registrar or any existing contracts. Names that do not register hooks are completely unaffected.

## Security Considerations

Hook contracts receive a callback from the notification registry and MUST NOT assume that the caller is trusted beyond verifying it is the canonical `NotificationRegistry` address. Hook implementations SHOULD be gas-bounded to prevent griefing via expensive callbacks. The registry SHOULD enforce a maximum gas limit per hook call.

Name owners SHOULD audit hook contracts before registration, as malicious hooks could waste deposited bounty funds or perform unexpected state changes when called.
